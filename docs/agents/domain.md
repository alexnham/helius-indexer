# Domain documentation

This is a single-context repository.

Before domain exploration, read root `GLOSSARY.md` when present,
then relevant decisions under `docs/adr/`.

If either is absent, proceed without creating placeholders.
Create domain documentation when terminology or decisions are resolved.

Use glossary terms consistently in code, tickets, tests, and designs.
Surface conflicts with existing ADRs explicitly.

`PROPOSAL.md` remains the requirements baseline.
Keep glossary definitions and architectural decisions in their
respective documents rather than duplicating them.
